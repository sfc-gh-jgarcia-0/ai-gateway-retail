Part 1

AI Capabilities in Snowflake

Everything an agent needs, built next to the data and governed by the same RBAC: business semantics, ML, LLM functions, agents and actions.

The Use Case: A Retail Analytics Agent

An athletic apparel brand wants merchandising, marketing and CX teams to ask questions in plain language and get governed, numeric answers

Goal

Answer "which channels drive margin?", "which campaigns pay back?" and "which segments will churn?" from one agent, using certified metrics and a real churn model, then act on the answer.

Who uses it

Business users in Snowflake Intelligence, and external agents (LangChain, coding agents) over MCP, all under their own roles.

Semantic Views: The Business Layer for AI

Define tables, joins, metrics and synonyms once; every agent and BI tool reuses them

CREATE SEMANTIC VIEW CUSTOMER_INTERACTIONS_SV
  TABLES (
    customers   AS DIM_CUSTOMER PRIMARY KEY (CUSTOMER_ID),
    interactions AS FACT_CUSTOMER_INTERACTIONS ...,
    churn_preds AS CHURN_PREDICTIONS          -- scores from the registered model
      COMMENT = 'Churn scores from CHURN_PREDICTION_MODEL' ...)
  RELATIONSHIPS (interaction_to_customer AS interactions(CUSTOMER_ID) REFERENCES customers, ...)
  METRICS (...)                                -- e.g. avg model churn score, predicted churners

CUSTOMER_INTERACTIONS_SV

Customer behaviour, segments, campaigns, CLV and churn scores.

CONVERSATIONAL_BI_SV

Revenue, orders, margins, stores, marketing efficiency and executive KPIs.

Why it matters for governance: Cortex Analyst only writes SQL against what the semantic view exposes, and the SQL runs under the caller's role. The semantic view is the boundary the agent can't step outside.

The agent is the contract

Tools, tool descriptions and orchestration instructions live in one CREATE AGENT spec. Add or change a tool there and every front end picks it up; no client code changes.

Many front ends, one agent

Write back in Snowflake

Queue a retention offer, flag customers for outreach, open a case row, refresh a segment. The proc owns the write; the agent never gets raw DML.

Reach outside Snowflake

The same proc can send email through a notification integration (SYSTEM$SEND_EMAIL) or call Slack, ServiceNow or a marketing platform through an external access integration.

Keep a human in the loop

Write to a PENDING_APPROVAL state and let a person or a downstream task release it. Return the campaign id so the agent can report what it did.

Guardrails: grant USAGE on the procedure only to roles allowed to act; validate and cap every argument inside the proc (prompt injection can shape inputs); put write tools on the agent rather than adding SYSTEM_EXECUTE_SQL; log each action to an audit table from inside the proc.
Part 2

Snowflake as the Central AI Control Plane

Not every agent will run inside Snowflake. Teams build in LangChain, coding agents and vendor copilots. The goal is one place that governs the data those agents touch and the models they call.

Tools: MCP server

Publish the governed Cortex Agent to any MCP client. Data access stays behind semantic views and RBAC.

Models: Cortex AI Gateway

One endpoint for every LLM call, with traces, cost attribution, model allowlists and per-user quotas.

Why External Agents Need a Control Plane

Sprawl of keys and endpoints

Every team wires its own provider keys into agents, notebooks and apps. Nobody can say which models are in use or who is calling them.

No visibility into agent behaviour

A single agent turn fans out into several model calls and tool calls. Without traces, slow or failing turns are guesswork.

Spend you can't attribute or cap

Token-based billing scales with verbose prompts and runaway outputs. Finance needs per-user and per-team attribution and hard limits.

Optimization without evidence

Prompt and model choices are made by intuition. Teams need a repeatable way to prove a cheaper config keeps answer quality.

The Control Plane Architecture

External agent, Snowflake-native tools, one governed inference path

LangChain agent (ChatOpenAI) + live_agent.py
Trace Analyzer app (Streamlit in Snowflake)
↓
Cortex AI Gateway SNOWFLAKE
model allowlist, logging, payload capture
MCP server RETAIL_MCP
one tool: Cortex Agent (2 Analysts, churn model scores)
↓

Pattern: Inference goes through the gateway; data access goes through MCP. Both authenticate as the same Snowflake user, so every token and every tool call is governed by RBAC and lands in telemetry you own.

Publishing the Agent to Any Client (MCP)

One governed tool: a Cortex Agent behind the MCP server

CREATE AGENT RETAIL_ANALYTICS_AGENT ...        # 2 Analyst tools: customer + churn, executive KPIs

CREATE MCP SERVER RETAIL_MCP FROM SPECIFICATION $$
tools:
  - name: retail_analytics_agent
    type: "CORTEX_AGENT_RUN"
    identifier: "CORTEX_GATEWAY_RETAIL_LAB.PUBLIC.RETAIL_ANALYTICS_AGENT"
$$;
No raw SQL tool: the client can't bypass the semantic views. Churn scores from the registered XGBoost model reach the client through the same tool. Clients connect over streamable HTTP at /api/v2/databases/<db>/schemas/<schema>/mcp-servers/<name> with the same PAT, and tools execute under the caller's role.
Two layers of orchestration: the external agent decides whether to ask Snowflake; the Cortex Agent decides how to answer. The gateway traces the first; Cortex Agent monitoring covers the second.

What is Cortex AI Gateway?

A governed inference endpoint that Snowflake provisions for you

Inference

OpenAI Chat Completions and Anthropic Messages APIs. Any client that can override its base URL works: SDKs, LangChain, coding agents.

Observability

One OpenTelemetry span per request in AGENT_TRACE_TABLE('SNOWFLAKE'): model, timing, tokens, status, and optionally the full prompt and response.

Cost management

Credits per request in AI_GATEWAY_USAGE_HISTORY, attributed to the calling user. Budgets and per-user quotas apply to the AI GATEWAY domain.

Access control

USAGE to send requests, MONITOR to read traces and usage. Model access still follows Cortex model RBAC.

Not the same as Cortex Inference: /api/v2/cortex accepts the same requests, but only traffic through /api/v2/aigateways/SNOWFLAKE gets the gateway's access control, traces and cost attribution.

One Endpoint, Two Standard APIs

/v1/chat/completions

OpenAI-compatible. All non-Claude models (OpenAI GPT-5 family and others your account can reach).

/v1/messages

Anthropic-compatible. Claude models only. Use a Bearer token, not the SDK's default x-api-key header.

from langchain_openai import ChatOpenAI

llm = ChatOpenAI(
    model="openai-gpt-5.4",
    base_url="https://<account-host>/api/v2/aigateways/SNOWFLAKE/v1",
    api_key=PAT,                                   # programmatic access token
    max_completion_tokens=4096,                     # GPT-5 family: not max_tokens
    default_headers={"traceparent": traceparent},   # groups one agent turn
)
Gotchas seen in the lab: hostnames must use hyphens, not underscores; GPT-5 models reject max_tokens; Claude sent to /chat/completions returns 400.

One turn, one trace: the ReAct agent makes a gateway call before and after each tool call. Sending the same traceparent on each groups them under one trace_id, which is what makes the turn debuggable.

Every Call is Traced

SELECT TRACE:"trace_id"::STRING                                   AS trace_id,
       RECORD:"name"::STRING                                       AS span_name,
       RECORD:"status":"code"::STRING                             AS status,
       DATEDIFF('millisecond', START_TIMESTAMP, TIMESTAMP)        AS duration_ms,
       RECORD_ATTRIBUTES:"gen_ai.usage.output_tokens"             AS output_tokens,
       RECORD_ATTRIBUTES:"gen_ai.input.messages"                  AS prompt   -- payload capture
FROM TABLE(AGENT_TRACE_TABLE('SNOWFLAKE'))
WHERE TIMESTAMP > DATEADD('hour', -1, CURRENT_TIMESTAMP());

From Telemetry to a Better Agent

The closed loop the Trace Analyzer app runs

1. Observe
Traces + usage by user, model, trace
→
2. Diagnose
Advisor: latency, errors, token bloat
→
3. Experiment
Replay eval set, baseline vs candidate
→
4. Compare
Quality, p50/p95, tokens, errors
→
5. Promote
Client config + gateway allowlist + quota

Evidence, not intuition

Every experiment call carries its own traceparent, so each result row in OPTIMIZATION_RESULTS links back to its gateway span.

Quality gate

An AI_COMPLETE judge scores each answer 0-1 against EVAL_PROMPTS.EXPECTED; a candidate is promoted only if it stays within 0.05 of baseline.

Typical wins

Cap max tokens, constrain verbosity in the system prompt, or move simple workloads to a smaller model in the same family.

Governing Spend: Attribute, Cap, Enforce

Attribute

Every gateway request lands in AI_GATEWAY_USAGE_HISTORY with its credits, model, tokens and calling user. A COST_CENTER tag on users turns that into chargeback by team.

Cap

Budgets track team spend (scoped by the same tag). Per-user quotas set daily, weekly and monthly credit limits on the AI GATEWAY domain, with notifications on actual or projected spend.

Enforce

With block enforcement on, a user at the limit is denied by the platform: HTTP 403, "exceeded the usage quota limit", with the restore time. The block clears at the cycle reset, or 5-10 minutes after the limit is raised.

Enforcement lands within minutes of the spend, not on each request, so a user can briefly overshoot; size limits with headroom. One limit applies to every user in a quota: use a tier tag and a second quota for heavier users.

Admin Controls

ALTER AI GATEWAY SNOWFLAKE FROM SPECIFICATION $$
schema_version: 1
models:
  - name: '*'                     # or an explicit allowlist
logging:
  enabled: true
  enable_client_telemetry: true
  capture_payload:
    request_response: true
$$;                              -- replaces the whole spec

GRANT USAGE   ON AI GATEWAY SNOWFLAKE TO ROLE app_team;      -- send requests
GRANT MONITOR ON AI GATEWAY SNOWFLAKE TO ROLE platform_ops;  -- read traces/usage
Spend controls (budgets, per-user quotas, block enforcement) are covered in Governing Spend.
USAGE is granted to PUBLIC by default. Revoke it to restrict who can send traffic; revoking USAGE is also how a budget action can cut a team off.

When to Use What

AI Gateway

  • External agents, SDKs, coding agents
  • Need traces, attribution, quotas
  • Standard OpenAI / Anthropic clients

MCP server

  • Give any agent governed Snowflake tools
  • Two Analysts and ML scores behind one Cortex Agent tool
  • No raw SQL tool to bypass the semantic view

Cortex Agents

  • Snowflake-hosted orchestration
  • Snowflake Intelligence front end
  • Built-in agent monitoring

Next Steps

1. Turn on logging

Set logging.enabled and capture_payload in the gateway spec, and grant MONITOR to the team that owns observability.

2. Point one agent at the gateway

Swap the base URL of an existing OpenAI or Anthropic SDK client and send a traceparent header per turn.

3. Run the optimization loop

Pick the top Advisor finding, replay an eval set with a candidate config, and promote it only if quality holds.

4. Add guardrails

Pin the model allowlist, then add a per-user quota with block enforcement and a shared-resource budget per team.

Govern the path, observe every call, and let the telemetry tell you which prompt and model to ship.
